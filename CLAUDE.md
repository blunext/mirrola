# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project goals

Mirrola turns a self-managed WordPress blog (`olamundo.pl`) into a static site. Since 2026-11-23 `olamundo.pl` is that static site on Cloudflare Pages; the WordPress it is made from runs locally in Docker (`wordpress/`) and is the source of truth. The old shared hosting was shut down in 2026-11; the source of truth is the latest restic snapshot in Cloudflare R2. There are two goals:

1. **Static mirror → Cloudflare Pages.** Crawl the WordPress site, rewrite every same-host link to a root-relative path, strip WordPress/Cloudflare cruft, and write a self-contained tree that can be deployed to Cloudflare Pages. This is what the Go crawler does.
2. **Portable WordPress → crawl → publish.** WordPress (files + DB) lives as restic snapshots in Cloudflare R2 and runs in Docker on any computer that has Docker (`make start` restores the latest snapshot, `make stop` / `make snapshot` push the changes back). New posts get written there, then the crawler mirrors that instance and the output goes to Pages (`make publish` / `make release`). Works on the owner's Mac (README checked on an empty Docker 2026-11-26); the second author (Windows: local Docker/WSL2 or an on-demand cloud instance, not decided) is not set up yet.

## Working rules

- **Anything that deletes or may overwrite files runs in Docker, never on the host.** The make targets already do (tools container). For your own tests use throwaway containers (`golang:1.27`, or the `olamundo-tools` image) with copies, never the real volumes (`wp_files`, `site`, `db_data`), and put the test scenario in a script file. On the host, only `go build`, `go vet` and `make -n`. `~/priv/olamundo` is the old site repo checkout (no longer used; removed in the core's cleanup step).
- **Commit only when the owner asks; never push.** Leave changes uncommitted and say so. In the site repo (`blunext/olamundo`, private; the `site` volume) a push to `development` deploys the preview (https://development.olamundo-3xg.pages.dev) and a push to `main` deploys olamundo.pl.
- **The owner runs the commands, one step at a time.** Give the command for the current step and wait for the result; run things yourself only when the owner says so. Read-only inspection to answer a question is fine.
- **Publishing stays manual:** `make crawl` → `make serve` (the owner checks locally) → `make publish` (preview) → the owner checks the preview → `make release` (olamundo.pl). Don't chain or automate these steps.
- **Proving a fix:** a test that fails on the old code (run it in a `git worktree` of `HEAD`) plus a full crawl of the local WordPress with the old and new binary (in a throwaway container, like `make check` does), comparing their output.
- **The owner writes in Polish; reply in Polish.**

## Commands

```bash
make crawl                                    # site repo (volume "site", shallow clone of blunext/olamundo) reset to origin/development (also dropping a commit whose push failed: it is regenerated), emptied (top-level dotfiles and Pages config kept), local WordPress crawled into it (DELAY=0, CONCURRENCY=10; STRICT=1 fails on dead links/collisions); a complete crawl leaves a marker that make publish requires
make serve                                    # preview the crawl on :8081 (PORT=)
make publish [MSG=...]                        # git add -A + commit + push of development (refuses on another branch); Pages deploys the preview
make release                                  # fast-forward main to origin/development (what the preview shows) and push it (no --force; deepens the shallow clone until main is an ancestor of development, refuses if it isn't); Pages deploys olamundo.pl
# Hand-written site files (_redirects, _headers, .gitignore) are edited on GitHub or in a separate clone of blunext/olamundo, never in the
# volume: make crawl resets it to origin/development and keeps them as they are there.
make start                                    # latest R2 snapshot → local WordPress (wp_files volume: only differences; DB replaced; wp-config.php/.htaccess from wordpress/config), then start it; unsnapshotted changes are lost. Leaves the marker .olamundo-restored in the volume; make snapshot refuses without it (a stock core from a plain "docker compose up" on an empty volume must never become the latest snapshot)
make stop [MSG="..."]                         # asks "push to R2? (t/n)" (t → make snapshot; a failed snapshot stops nothing), then docker compose stop
make snapshot [MSG="..."]                     # restic backup of the local WordPress to R2 in the tools container: DB dump + public_html, then retention; MSG becomes a tag
make snapshots                                # list snapshots
make snapshot-check [READ_DATA=1]             # restic check (READ_DATA=1 reads every pack)
make snapshot-init                            # create the restic repository (new bucket only)
make check                                    # crawl the local WordPress into a throwaway dir and compare it with the site repo at BASE (default origin/development, fetched first; shallow clone, so only branch tips); report in .check/report.txt; run after every plugin/WP/PHP change
# crawl/publish/release/check use this computer's deploy key (wordpress/deploy/olamundo_deploy_key, gitignored; one key per computer,
# write access to blunext/olamundo only) and commit as "olamundo publish ($PUBLISHER)" <noreply@olamundo.pl> (PUBLISHER in .env).

go build -o mirrola .                         # build crawler CLI
go run . -url http://localhost:8000 -site-url https://olamundo.pl -dir ./static [-strict] [-delay 2] [-max-depth N] [-concurrency N]
go run ./server -dir ./static [-port N]       # preview static output (default :8080) (dir → index.html, trailing-slash redirect)

go test ./...                                 # all tests live in crawler/
go test ./crawler -run TestCrawler_BasicFlow  # single test
go test ./crawler -coverprofile=crawler/cover.out && go tool cover -html=crawler/cover.out
```

## Crawler architecture (`crawler/`)

- **Entry:** `main.go` parses flags and calls `crawler.Init(...)` and then `crawler.Run(ctx)`.
- **State is split between package globals and `*Config`.** This is a deliberate refactor that is only half done. `config.go` holds globals (`client`, `limiter`, `visited`, `tasksWg`, regexps, and `cfg`). `types.go` holds the `Config` struct. Newer code is written as `Config` methods (`ProcessCSSFile`, `ProcessInlineJS`, `ProcessSrcSet`, `GetOutputPath`, `ToRelative`, `SameHost`, …), and older code is free functions reading globals. Regexps get compiled in both places (`initRegexps` and `Config.InitRegexps`). Tests that touch free functions must set the globals up themselves. Continue migrating toward `Config` rather than adding new globals.
- **Work loop (`crawler.go`):** a buffered `tasks` channel feeds N workers. `enqueueLink` normalizes the URL (`fixPath` + `normalize`), dedups it through `visited`, enforces `max-depth`, and calls `tasksWg.Add`. When `tasksWg` drains, a goroutine cancels the context and closes the channel. If the queue is full, `enqueueLink` hands the send to a goroutine instead of blocking: workers are the only producers, so blocking could deadlock the pool.
- **Redirects (`processURL`):** `http.Client` follows them silently. Content is saved under the requested URL's path (what pages link to), but relative links resolve against the final URL (`resp.Request.URL`, via `processHTMLAt`) and collisions are checked on the final URL. An HTML page redirecting to another host is not saved (`offsiteRedirectError`); for the start URL this is fatal, which catches a local WordPress whose `siteurl`/`home` still point to production. Assets redirected off-site (CDN) are saved.
- **Errors (`Run`):** dead links (HTTP 404/410, `isDeadLink`) and off-site page redirects (`isSkippable`) are logged with the referring page (`task.from`) and listed at the end; they don't stop the crawl unless `-strict`, or unless it's the start URL. Every other failure (403/429 from a WAF, 5xx, network, write errors) is fatal: the first one (`sync.Once`) cancels the crawl and `Run` returns an error. Cancelling the parent context (Ctrl-C, via `signal.NotifyContext` in `main.go`) also returns an error. Rule: an incomplete mirror must never exit 0, because a deploy step would publish it. After workers stop, `Run` drains the queue so `tasksWg` returns to zero and a later `Run` starts clean (`Init` also resets `visited` and `limiter`).
- **Seeds (`seeds.go`), only when the start URL is the site root:** besides the start page, the crawl fetches `/robots.txt` (optional: a 404 is fine even with `-strict`) and follows its `Sitemap:` lines. XML sitemaps (`<urlset>`/`<sitemapindex>`) are parsed for same-host `<loc>` entries (pages and nested sitemaps, enqueued as links) and `<?xml-stylesheet href>` (the XSL, as an asset), so pages nothing links to are mirrored too (that is how 4 forgotten plugin demo pages showed up; they were deleted in 2026-11). Sitemaps and robots.txt keep absolute URLs; when crawling a copy `ToPublicText` turns them into https://olamundo.pl. The 404 probe requests `notFoundPath` (`/mirrola-404-check/`) and saves the 404 HTML page as `/404.html` (Pages serves it for missing paths; without it Pages answers them with the home page and 200); a site that answers 200 gets only a warning. RSS feeds are disabled in WordPress; `_redirects` in the site repo (hand-written, kept by the crawl's cleanup) redirects `/feed/`, `/comments/feed/` and `/*/feed/` like the old WordPress did. Deliberately not covered (decided 2026-11-23): `/comments/feed` and `/*/feed` without the slash answer 404 (feeds don't exist, so 404 is honest), and old `/?p=ID` links show the home page (WordPress redirected them to the post; `_redirects` cannot match query strings, and the blog never shared short links, so nothing points there). Disqus still uses `?p=ID` as thread identifiers, which is unrelated to redirects.
- **Depth semantics:** assets (img/css/js/fonts found in HTML or CSS) inherit the page's depth. Only `<a href>` links increase depth.
- **Dispatch by Content-Type (`processURL`):**
  - HTML goes to `processHTML` (`html.go`), which calls `filterDocument` and then `rewriteLinks`.
  - CSS goes to `ProcessCSSFile` (rewrites `url(...)`).
  - Everything else is streamed straight to disk.
  - `-delay` throttles page requests before they are sent (one shared limiter). Whether a URL is a page is guessed from the URL (`looksLikePage`: trailing `/`, no extension, `.html`/`.htm`/`.php`); static files are never delayed.
- **`filterDocument`** removes the configured `unwantedTags` (shortlink, pingback, EditURI, oEmbed, wp-json), Cloudflare challenge scripts, comment-reply, WP emoji JS and CSS, and all HTML comments. Extend `unwantedTags` / `shouldRemoveScript` / `shouldRemoveStyle` to strip more.
- **Link rewriting:**
  - Same-host URLs become root-relative paths (`ToRelative`). External hosts stay absolute. Exception: `<link rel="canonical">` gets the full URL on the public site (`ToPublicURL`, `-site-url`, Makefile `SITE_URL`, default `-url`), so *.pages.dev previews and a local-WordPress crawl still point search engines at https://olamundo.pl/….
  - Fragments are kept in the written link (`resolveURL` preserves them; `urlKey` drops them for fetching/enqueueing). Fragment-only references (`#_ftn1`, `#`, `url(#clip)`) are left exactly as written (`isFragmentOnly`).
  - Rewriting covers `href`, `src`, `srcset`, inline `style`, `<style>`, `<source>`, and inline `<script>`.
  - **Crawling a copy (`-url` host ≠ `-site-url` host, e.g. the local WordPress):** after link rewriting, `ToPublicText` (`publicurl.go`) replaces the source address with the public one in every saved HTML page, CSS file and text asset (JS, JSON, XML/sitemaps). It handles every form the source address is written in: plain, `\/`-escaped, URL-encoded (`http%3A%2F%2Flocalhost%3A8000`), `\u002F`-escaped and protocol-relative. That catches what isn't a link: Disqus `disqusUrl`, Facebook/LinkedIn share links, sitemaps, which leaked `localhost` in 462 pages before. If a saved file still contains the source hostname afterwards (an unknown form, e.g. double encoding), it is logged and `Run` fails at the end, so the mirror can't be published. When crawling the public site itself this is a no-op.
  - Inline JS handling targets JSON-escaped `https:\/\/…` URLs (Simple Lightbox plugin) and re-escapes slashes after rewriting.
- **Output paths (`filesystem.go` `GetOutputPath`):**
  - Extensionless HTML URLs become `path/index.html`.
  - A missing extension is inferred from the Content-Type.
  - Paths are NFC-normalized and Polish diacritics transliterated (`removeDiacritics`: `łódź` → `lodz`), so files and links are plain ASCII and NFC/NFD spellings collapse to one file. (A percent-encoded `-safe-filenames` mode existed but was removed: static hosts decode the URL, so literal `%XX` file names never matched.)
  - The query string is never part of the file name (static hosts ignore it); links keep it. A `-rewrite` mode that baked queries into file names existed but was removed: it computed file names and links with different rules (404s), and the site has no pages that differ only by query.
  - **Invariant:** the link from `ToRelative` must resolve to the file written by `GetOutputPath`. Both go through `normalizePath`; `TestLinkMatchesWrittenFile` (`consistency_test.go`) checks it the way a static host resolves links (decode path, drop query, dir → `index.html`).
  - **Hidden paths are never written** (`checkNotHidden` in `claimOutput`): any path component starting with `.` is refused (`hiddenPathError`, skipped like a dead link, fatal with `-strict`). The output dir is a git repo, so a crawled `/.git/config` or `/.gitignore` would otherwise overwrite it; the crawl's cleanup keeps dotfiles too.
  - **Collisions (`collisions.go`):** `claimOutput` records which URL produced each output path. The same resource in NFC/NFD form is skipped silently; a different URL on the same path (e.g. `łódź.jpg` vs `lodz.jpg`, or `?ver=1` vs `?ver=2`) logs `[WARN]` and keeps the first file, or aborts with `-strict`. A `Config` built without `NewConfigFromGlobals` has no registry and doesn't track.
- **HTTP (`http.go` `fetch`):** one GET per URL (no HEAD: it used to precede every GET and its result was never used). On a 404 it retries once with the path's Unicode normalization flipped (NFC↔NFD), because Polish characters in WordPress upload filenames are inconsistent. `writeFile` writes to a temp file, then renames it, and cleans up on failure.

## Regression check (`make check`, `sitecheck/`, `olamundo.sh site-check`)

- Runs in the tools container on the compose network: extracts the baseline with `git archive BASE` from the site repo, crawls the local WordPress through `socat` on `localhost:8000` → `wordpress:8000` (a TCP forward keeps the Host header; WordPress redirects any other host; `make crawl` uses the same forward), then runs `sitecheck -old baseline -new crawl -forbid localhost:8000`.
- `sitecheck` fails (exit 1) on removed pages, changed *visible* text (title, body text, image alt), broken internal links that weren't broken in the baseline (resolved like a static host), and forbidden strings. Markup-only changes are reported as tag patterns with page counts (numbers and the page's own path masked, `?ver=`, nonces, Simple Lightbox's per-request image ids, HTML/XML comments and whitespace ignored; this normalization is only for comparing, the crawler output keeps them): that is how the missing lightbox layout showed up. When pages differ only in numbers (masked away), the report shows each changed number with context instead, as `~ N  …context[old → new]context…` (e.g. the WordPress version in Disqus's `embedVars` after a core update). Asset and file changes are informational.
- Workflow for any WordPress change (plugin removal/update, core, PHP image): change one thing, `make check`, read the report.

## WordPress side (`wordpress/`)

- `docker-compose.yml` runs MariaDB 10.6, `wordpress:7.1.5-php8.4-apache` on `:8000` (the image only provides PHP and Apache: the WordPress files are in the volume, updated in wp-admin; keep the tag's WordPress version equal to the volume's, bump it after a core update) (Apache listens on 8000 *inside* the container too, `wordpress/apache/*.conf`: WordPress requests its own address `http://localhost:8000` from inside the container, Simple Lightbox fetches its `layout.html` and WP-Cron spawns itself this way; with Apache on 80 these failed silently and 31 gallery pages lost the lightbox layout), with credentials from `wordpress/.env` (gitignored). The WordPress files are the Docker volume `wp_files` (`/var/www/html`), filled by `make start` from the latest R2 snapshot; the session rule is: `make start` → write → `make snapshot`.
  - Only `wp-config.php` and `.htaccess` are tracked, in `wordpress/config/`; `make start` copies them into the volume every time (git wins over the snapshot's copy). Nothing uses the old bind-mounted `wordpress/public_html/` any more.
  - **Tools container** (`wordpress/tools/`: Dockerfile + `olamundo.sh`, compose service `tools`, profile `tools`): WP-CLI image plus restic, git and this repo's `mirrola`, `sitecheck` and server binaries, built from the repo root (`Dockerfile.dockerignore` whitelists the Go sources). Make runs it with `docker compose run --rm --build tools <command>`. It gets `wordpress/.env` through `env_file` (the calling shell can't override it, unlike `${VAR}` interpolation), mounts the `wp_files` volume at `/data/public_html` (read-only in `tools`, writable in `tools-restore`, which only `make start` uses), runs as uid 33 (Apache's www-data, so restored files stay writable for uploads), keeps restic's cache in the `tools_cache` volume, and writes the DB dump to a tmpfs (`/data/db`), so it never touches the disk. Only Docker is needed on the host. Plan (docs/plan-wordpress-data.md, "Decyzje o rdzeniu"): WordPress files move to a Docker volume, `make start`/`make stop`, crawl/publish from the container.
  - **Backups: restic** (`make snapshot`, `olamundo.sh snapshot`), the only repository is the Cloudflare R2 bucket `olamundo` (`s3:https://<account-id>.r2.cloudflarestorage.com/olamundo`, R2 token scoped to that bucket, Object Read & Write). `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` come only from `wordpress/.env` (via `env_file`); the script refuses any repository but that bucket (regex on the URL), so it can't touch the owner's private restic setups. A snapshot holds `/public_html` (without `wp-content/{cache,wflogs,upgrade,upgrade-temp-backup}` and `.DS_Store`) and `/db/olamundo.sql` (a `wp db export` with localhost URLs, in a tmpfs), `--host olamundo-wp`; then `forget --group-by host --prune --keep-last 10 --keep-weekly 8 --keep-monthly 12`. `.env` is not in the backup: its values are in the owner's password manager. Restoring is `make start` (verified 2026-11-24: start on an empty volume, then `make check` identical to the published site).
  - Cleaned up 2026-11-23, plugins reviewed 2026-11-25. Plugins left: advanced-custom-fields (deactivated 2026-11-26, `make check` identical; no field groups, nothing reads its values: `youtube_video_id`/`video_service`/`page_header`/`page_sidebar` in 5 posts/pages from 2014, left by an old theme, stay in `wp_postmeta`; can be deleted), classic-editor, disable-everything (disables RSS feeds, REST API, oEmbed, XML-RPC auth methods, generator, shortlinks, manifest, dashicons, PDF thumbnails), disqus-comment-system, filenames-to-latin (latin file names on upload), google-sitemap-generator (`sitemap.xml`/`sitemap.html`; WordPress's own `wp-sitemap.xml` exists too, both in robots.txt: check Google Search Console before dropping one), shortcodes-ultimate (galleries; bundles Freemius: its `fs_*` options are live), simple-lightbox (the only image lightbox), wild-book-bundle (theme widgets, share buttons); theme wildbook; mu-plugin clean-archives-lite. Removed 2026-11-25: disable-xml-rpc-pingback, font-awesome (loaded 2 stylesheets from use.fontawesome.com, no icon used), fancy-box (duplicated Simple Lightbox). `xmlrpc.php` answers (pingback included); irrelevant locally and for the static olamundo.pl, but block it for a cloud instance. Orphan tables/options of removed plugins were dropped. `wp-config.php`: no `WP_TEMP_DIR` (temp files go to the container's /tmp, not uploads), `WP_DEBUG` off (fatal errors still reach `docker logs wordpress`), `WP_POST_REVISIONS` 3.
  - **No secrets in git** (this repo is public). `wp-config.php` reads DB credentials and the 8 keys/salts with `olamundo_env()` (`getenv`, dies with "Missing environment variable X" when unset). Values live only in `wordpress/.env`; `.env.example` lists the names. Compose passes them to `wordpress` through the `x-wp-env` anchor with `${VAR:?}`, so a missing value stops compose; the tools services get the whole `.env` (`env_file`). Local salts are random, not production's (until 2026-11-18 the committed wp-config.php held the production salts; they were rotated on the host).
- `wordpress/README.md` (Polish, for the authors): setting up a new computer (.env, deploy key), a session, publishing, WP-CLI. The initial import from the old host (`ssh om`, tar, mysqldump; `sync-from-host.sh`, removed) is in git history up to e01a86f; the host is no longer the source.
- **URLs in the database are rewritten with WP-CLI `wp search-replace` after importing the original dump**, not in the `.sql` file. WP-CLI runs in the tools container: `cd wordpress && docker compose run --rm --entrypoint wp tools --path=/data/public_html …` (WordPress files read-only there, DB writable). WordPress stores PHP-serialized strings (`s:<len>:"…";`), and WP-CLI unserializes, replaces and serializes them again.
  - Tested 2026-11-18 on the 2024-12-30 dump in throwaway containers: 0 of 1898 serialized values unreadable after `search-replace`. The only warning was a skipped `GoogleSitemapGeneratorStatus` object, a plugin class not loaded. What still contains `olamundo.pl` is `guid` (skipped on purpose) and Wordfence `wp_wf*` tables.
  - **`replace/` is kept but broken; don't use it on a dump.** It measures string lengths on the SQL-escaped text (backslashes counted twice) and rewrites every length, even where the text didn't change. On the same dump it left 1239 serialized values unreadable by PHP (1142 in `wp_postmeta`). `wordpress/wordpress.sql` is its output and is corrupted. `sed` on a dump breaks every serialized string it changes.
- SQL dumps (`wordpress/*.sql*`) and the built `mirrola` binary are untracked artifacts. Don't commit them.
- To mirror the local instance: `make crawl` (crawls `http://localhost:8000` with `-site-url https://olamundo.pl` into the site repo). Links are root-relative, so the output does not depend on the source host. If the instance's `siteurl`/`home` still point to production, the crawl fails with an off-site redirect error.

## Cloudflare Pages and the domain

- Pages project `olamundo` (subdomain `olamundo-3xg.pages.dev`; `olamundo.pages.dev` belongs to someone else), connected to GitHub `blunext/olamundo` (private; the `site` volume). Production branch `main` → olamundo.pl; branch `development` → preview https://development.olamundo-3xg.pages.dev. Deploy status: `gh api repos/blunext/olamundo/commits/<sha>/check-runs` (a commit deployed as preview and then released may not get a second check run; check the site itself).
- DNS is in Cloudflare: `olamundo.pl` is a proxied CNAME to `olamundo-3xg.pages.dev` (Pages custom domain); `www` → `olamundo.pl` is a Cloudflare Redirect Rule (301, keeps path and query), independent of any origin. Always Use HTTPS is on. The domain has no mail: no MX, SPF `v=spf1 -all`, DMARC `p=reject` (since 2026-11-23); no DNS records for the old host's services (mail, ftp, cpanel) remain.
